# MemGPT: Towards LLMs as Operating Systems

<https://arxiv.org/abs/2310.08560>

Packer, Wooders, Lin, Fang, Patil, Stoica, Gonzalez. University of
California, Berkeley. 2023.

## Core ideas

The analogy is the paper, and it is a good one. An operating system gives
a program the illusion of more memory than physically exists by paging
between RAM and disk. MemGPT gives a model the illusion of more context
than its window holds by paging between the prompt and external storage.
The window is treated as a **constrained memory resource** rather than as
a given size.

The hierarchy has two tiers. **Main context** is the prompt: whatever is
in it is visible to the model this turn. **External context** is
everything else, and it must be explicitly moved in before the model can
see it.

Main context is divided into three contiguous regions, and the division
is the design:

- **System instructions.** Read-only. Describes the memory hierarchy,
  what each tier is for, and how to call the functions that move data
  between them.
- **Working context.** A fixed-size read/write block, writable only
  through function calls. Holds the durable facts: who the user is, what
  they prefer, what the agent has committed to.
- **FIFO queue.** The rolling message history. Its first slot holds a
  **recursive summary** of what has already been evicted.

External storage is likewise split: **recall storage** holds the full
message history, and **archival storage** is a read/write database for
arbitrary text the agent chooses to keep.

**The model manages its own memory.** This is the claim that makes it
more than a context-trimming library. Memory edits and retrieval are
self-directed: the model calls functions to write a fact into working
context, to search recall storage, or to file something in archival
storage, and it decides when. The system instructions carry the
description of the hierarchy and the function schemas that make this
possible, which means the memory policy is written in a prompt.

Two mechanisms make it run.

- **Memory pressure as an event.** When the prompt approaches its limit,
  the system inserts a warning message, giving the model a chance to save
  what matters before anything is lost. Past a flush threshold the queue
  manager evicts a block of messages and folds them into a new recursive
  summary. Evicted messages remain in recall storage and stay searchable;
  what is lost is only their presence in the window.
- **Event-driven control flow with chaining.** Inference is triggered by
  events, which include user messages, system warnings, and scheduled
  timers, so the agent can act unprompted. A function call carries a flag
  requesting control back immediately, which lets the model chain calls —
  paging through results, collating from several queries — before
  yielding. Without the flag it yields and waits for the next event.

Function results, **including runtime errors** such as trying to write to
a full working context, are fed back to the model as part of the next
input.

## What problem it solves

The context window is finite, extending it costs quadratically, and — the
sharper half of the argument — even when the window is large, models do
not use the extra space well. Given that, the paper argues the productive
move is not a longer window but a **policy** for what occupies the one
you have.

The insight worth taking is that this is a systems problem with a
literature. Paging, eviction, tiering, and interrupts are old solved
problems, and treating the window as physical memory imports all of that
vocabulary at once.

## Limitations

The paper has no limitations section, so these read out of the design
rather than off the page.

- **The policy lives in a prompt.** The memory hierarchy and its rules
  are described in system instructions and executed by the model's
  judgment. Nothing enforces them, so this inherits every reliability
  problem of instruction following, and the paper's own note that runtime
  errors are returned to the processor is a sign of how often the model
  gets it wrong.
- **Eviction is lossy and it compounds.** The recursive summary is a
  summary of summaries. Each flush compresses again, so an early detail
  that no reflection preserved degrades with every cycle even though the
  raw message technically remains in recall storage.
- **Self-directed memory means self-inflicted loss.** If the model does
  not recognize a fact as worth saving when the pressure warning arrives,
  it is gone from the window and only recoverable by a search that the
  model must think to run.
- **Working context is fixed-size**, so the durable tier has a hard
  ceiling and overflow surfaces as an error the model has to handle.
- **It depends on reliable function calling**, which was much less
  certain when this was written than it is now.

The paper's own forward look is about better memory tier technologies and
**improved control flow and memory management policies**, which is a fair
admission that the policies here are a first pass.

## What this means in practice

1. **The question that separates this from retrieval: is the knowledge
   outside the run, or produced by it?** A static corpus of documents,
   policies, or product data is 2005.11401's problem: fetch on demand,
   cite, done, and your code decides. What the user said three sessions
   ago, what was decided, what has already been tried — that is produced
   by the run, it accumulates, and no similarity search over a fixed
   index will manage it. The hard part there is not finding, it is
   **deciding what to keep**.

2. **Tier your context deliberately, because the tiers have different
   costs.** Verbatim in the window, compacted to a digest, or outside
   entirely with a pointer. Most long-running agent context belongs in
   the third tier and ends up in the first by accident, which is the
   default failure and it costs money on every single turn.

3. **Cut by value, not by age.** This is the correction the FIFO design
   invites and does not itself make. A digest that replaced twenty older
   turns is by construction the oldest non-anchor item in the window, so
   an evict-oldest policy throws away exactly the thing you compressed and
   keeps the small talk that came after it. Give each item a tier and
   sacrifice raw turns before compressed ones.

4. **Some things must never be evicted.** The system prompt, the task,
   and any constraint the agent is held to are anchors. A budgeter that
   trims by age alone will eventually drop the instruction defining the
   job, and the symptom is the agent getting worse for no visible reason.

5. **Treat the memory-pressure warning as a design pattern, not an
   implementation detail.** Giving the model a chance to save state
   *before* eviction, rather than truncating silently, is the difference
   between graceful degradation and data loss. The general form: whenever
   your harness is about to destroy context, tell the model first.

6. **Compaction must actually save space, and it can fail to.** An
   extractive summary over a history where nearly every sentence carries
   an identifier can come out longer than what it replaced. Cap the
   digest, compare it against what it is replacing, and decline to run
   when it does not win. Compaction that saves nothing is pure loss.

7. **A pointer is only a tier if it can be followed.** The third tier
   works when the pointer names the note, says how large it is so the
   model can judge whether opening it is worth the tokens, and comes with
   a tool that opens it. A reference with no way to resolve it is a dead
   end wearing a tier's clothing.

8. **Trimming breaks the message shape, and the breakage looks like an
   unrelated bug.** Dropping an assistant turn between two user turns
   leaves two user messages adjacent; dropping the first user turn can
   leave the list starting with an assistant message. Normalize that
   where you trim, not in a retry after the API complains. There is a
   stranger failure too: a history trimmed by age alone opens mid-thread
   with decisions already asserted and an assistant already agreeing,
   which is shaped exactly like a planted conversation, and a model may
   decline it outright. A digest fixes this incidentally, because it
   declares what it stands in for instead of leaving a silent gap.

## What it leads to next

Nothing in this library extends it. Reading outward:

- **2005.11401** is the other half of the topic and the contrast that
  defines it: retrieval from a fixed corpus your code queries, versus
  memory over the run's own history that the model manages.
- **2304.03442** applies memory to a population of agents, where
  reflection over accumulated observation becomes the mechanism rather
  than the housekeeping.

The OS framing also points at `03-self-correction`: a reflection is a
write to durable memory, and 2303.11366's bounded experience buffer is
the same fixed-size working context with the same eviction question left
open.

## Connection to the lab

`papers.yaml` maps this to
`labs/track-2-tools-context/11-context-memory`, and that lab is the
practitioner's version of this paper with the OS metaphor removed and the
policy questions sharpened.

**The lab's three tiers are this paper's hierarchy restated as a
decision.** What must be in the window verbatim, what can be compacted
into a digest, what belongs in a file with only a pointer in the window.
Where the paper describes a mechanism, the lab asks you to classify your
own content, which is the part that transfers.

**`budget_messages` supplies the eviction policy the paper leaves to the
model's judgment.** Anchors are never dropped; everything else goes by
tier, oldest first within a tier, so raw turns are sacrificed before the
digest. That ordering is point three, and it is a correction to a plain
FIFO. The lab even guards the guard: a final pass that can drop any
remaining non-anchor message, so a typo in a tier name cannot pin
something in the window forever.

**`compact` adds the check the recursive summary needs.** Cap the digest
and decline to compact when it would not be smaller than what it
replaces, and skip compaction entirely when the raw history already fits.
The paper flushes on a threshold regardless; the lab asks whether the
flush is worth it.

**`Scratchpad` and `scratchpad_index` are archival storage made
concrete**, and the lab's requirement that a pointer name the note, its
size, and the tool that opens it is what point seven demands. Paired with
`READ_NOTE_TOOL` and `run_read_note`, that is this paper's self-directed
retrieval built out of ordinary tool calls rather than a bespoke runtime.

Two things the lab has and the paper does not. `to_api_messages`
normalizes the message shape that budgeting broke, which is point eight.
And the lab's closing warning about measurement: an empty answer is not a
bad answer, a refusal or a run that ended on `max_tokens` has nothing to
do with what was in the window, so read `stop_reason` before concluding
that a context strategy failed. That is the difference between tuning a
budget and tuning the wrong thing entirely.
