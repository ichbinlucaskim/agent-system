# AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation

<https://arxiv.org/abs/2308.08155>

Wu, Bansal, Zhang, Wu, Li, Zhu, Jiang, Zhang, Zhang, Liu, Awadallah,
White, Burger, Wang. Microsoft Research, Pennsylvania State University,
University of Washington, Xidian University. 2023.

## Core ideas

A framework, not a method. The claim is that **multi-agent conversation**
is a general enough abstraction to build most LLM applications on, and
the paper is an argument for that abstraction plus the library that
implements it.

Two concepts carry it.

**Conversable agents.** An agent is something that can send and receive
messages, and it may be backed by a model, by a tool, by a human, or by
any combination. That last part is the idea worth taking: a person
approving a step and a function returning a value are **the same kind of
participant** as a model, differing only in what produces the reply. A
human in the loop is not a special case bolted onto the architecture; it
is an agent that happens to be slow.

**Conversation programming.** Building an application is two steps:
define the agents with their roles and capabilities, then program how
they interact. The interaction is expressed as a mix of natural language
and ordinary code, so control flow can be a prompt where judgment is
needed and a Python conditional where it is not. Supported patterns
include two-party dialogue, group chat, and hierarchical arrangements,
static or dynamic.

The reasons offered for why conversation works as the primitive are
worth separating, because they are three different claims: chat-tuned
models can absorb feedback, so agents can critique each other; one model
configured differently exhibits different capabilities, so a set of
agents can be a set of configurations of the same model rather than
different models; and tasks decompose, so a conversation can carry the
partitioning and the reassembly.

That second point is the one most often missed. The agents in a typical
AutoGen application are **the same model with different prompts and
different tool sets**, which makes multi-agent much cheaper than it
sounds and also explains why it is not a diversity mechanism.

## What problem it solves

The gap was between demonstrations and construction. Multi-agent setups
had shown promise for divergent thinking, factuality, and validation, but
each was built bespoke. There was no common abstraction that spanned
domains and complexities, and no unified interface covering single-turn
and multi-turn, human-in-the-loop and fully automatic, static and
dynamic.

AutoGen's answer is that if you make the message the unit and let
anything that can reply be an agent, the same interface covers all of it.

## Limitations

The paper is a framework paper and reads like one; it has no limitations
section, so these read off the design and the demonstrations.

- **Generality is claimed by breadth of examples rather than argued.**
  The evidence is that many applications were built, which does not
  establish that conversation is the right abstraction for them, only
  that it is a sufficient one.
- **No account of when multi-agent is the wrong choice.** The framing
  makes adding an agent easy, which quietly makes it the default. The
  cost of an extra participant, in tokens and in latency, is not part of
  the analysis.
- **Conversation as control flow is hard to bound.** A pattern where
  agents decide who speaks next has no natural termination, and the
  failure mode is agents agreeing with each other in a loop.
- **The agents are usually one model in different costumes**, so the
  independence that would justify treating disagreement as evidence is
  not there.

## What this means in practice

1. **Take the abstraction, question the multiplicity.** The genuinely
   good idea is that a model, a tool, and a person are interchangeable
   participants behind one interface. That simplifies human approval and
   tool execution enormously and costs nothing. The separate claim, that
   your application should be several agents talking, needs its own
   justification every time.

2. **Ask what the second agent knows that the first does not.** A useful
   split gives each side something the other lacks: a different tool set,
   a different context, a different prompt with genuinely different
   instructions. If the answer is nothing, you have paid for a round trip
   to talk to yourself.

3. **The strongest reason to split is capability, not cleverness.** An
   agent that only needs to read can be given only read tools, and then a
   prompt injection in what it reads has no write tool to reach for.
   Restriction by construction beats instruction, and it is a better
   argument for a second agent than divergent thinking.

4. **Program the control flow you can, converse for the rest.** The
   framework's fusion of code and language is the right instinct in the
   right order: if you know the sequence, write it as a sequence; hand
   the decision to the conversation only where the decision genuinely
   requires judgment. A conversation is the most expensive control-flow
   construct available.

5. **Every conversation pattern needs a termination condition you
   wrote.** Group chat and dynamic speaker selection will not stop on
   their own. Turn limits, cost ceilings, and a no-progress check belong
   around any multi-agent pattern, and the run should report which one
   fired.

6. **Do not read agreement between agents as evidence.** When the
   participants are one model in different prompts, their agreement is
   correlated by construction. This is the crucial difference from
   2203.11171, where independent samples make agreement meaningful.

## What it leads to next

Nothing in this library extends it. Read it against **2304.03442**, the
other multi-agent paper here, and the contrast is the topic: there the
population is the object of study and coordination emerges, here the
population is an engineering decomposition and coordination is
programmed.

The abstraction lands most usefully in `06-environment-and-interface`,
since what distinguishes one agent from another in practice is the tools
it holds, and that is the subject of **2405.15793**.

## Connection to the lab

`papers.yaml` maps this to two labs, and together they are this paper's
claim broken into the part that is a workflow and the part that is
delegation.

**`labs/track-1-patterns/05-orchestrator-workers` is conversation
programming with the conversation removed.** A lead call plans, workers
execute, the lead synthesizes. That is a hierarchical pattern of the kind
this framework supports, written as explicit code rather than as a
dialogue, and it is the version to reach for first because the control
flow is inspectable.

The lab supplies the discipline the framework leaves out. **Treat the
plan as untrusted input**: validate its shape, cap the count, drop
duplicates before spending a worker call. A framework that makes spawning
easy needs that check more, not less. And the lab's warning that cost
grows quickly, one planning call plus N workers plus a synthesis whose
prompt contains all the worker output, is the accounting this paper does
not do.

**`labs/track-3-autonomy/13-subagents` is where the cost question gets
answered honestly.** That lab states plainly that delegation is not free,
that each child re-establishes context from scratch, and that for work
the parent could finish in a few tool calls the overhead exceeds the
benefit. It names the shape that pays, fan-out over genuinely independent
work with each child getting **its own subtask string**, and the
anti-pattern, handing every child the same question and relying on the
system prompt, which it calls prompt-splitting rather than fan-out.

Its `restrict_tools`, which returns only the tools a spec allows and
raises on a name the parent does not have, is point three implemented:
capability granted by construction rather than by instruction. The lab is
explicit that the parent holding `write_note` while the children do not
must show up in the tool lists rather than only in the prose.

The lab also ends where this paper does not: in a **measurement**. Run
the same task with and without delegation, record total tokens,
wall-clock, and answer quality. That comparison is the missing half of
any multi-agent claim.
