# 07 - Workflow, not agent

## Representative system

의도적으로 없습니다. 이 case는 이 라이브러리의 다른 어떤 것이 관련되기 전에 이미
배제했어야 하는 설계를 기술합니다.

## 이 archetype이 존재하는 이유

이 라이브러리의 다른 모든 case는 agent를 옹호하는 논변입니다. 순서대로 읽으면 출처
자료에는 없는 관성이 생기는데, 이 case는 그것을 멈추기 위해 존재합니다.

[T1] Anthropic의 Building Effective Agents는 이 구분을 직접적으로 긋습니다. workflow는
LLM과 tool이 미리 정해진 code path를 통해 조율되는 시스템이고, agent는 LLM이 자신의
프로세스와 tool 사용을 동적으로 지휘하는 시스템입니다. [T1] 그 지침은 가능한 가장 단순한
해법을 찾고 필요할 때에만 복잡성을 늘리라는 것이며, 이는 agentic system을 아예 만들지 않는
것을 뜻할 수도 있습니다. [T1] agentic system은 더 나은 작업 성능을 위해 지연과 비용을
맞바꿉니다. [T1] retrieval과 in-context example을 곁들인 단일 LLM 호출을 최적화하는 것으로
충분한 경우가 많습니다.

[T1] multi-agent system에 대한 후속 post는 더 직설적입니다. 여러 팀이 정교한 multi-agent
architecture를 만드는 데 몇 달을 투자한 뒤에야 단일 agent에 대한 개선된 prompting이 동등한
결과를 냈다는 것을 발견했습니다.

이 case가 다루고 다른 어떤 case도 다루지 않는 지점은 **만들지 않기로 하는 결정**입니다.
case 01부터 06까지는 "이 agent를 어떻게 설계해야 하는가"에 답합니다. 이 case는 "agent가
있어야 하는가"에 답하며, 라이브러리에서 정답이 자주 아니오인 유일한 질문입니다.

### 체크리스트

agent에 손을 뻗기 전에 이것을 돌리십시오. 각 항목은 질문과 선호되는 답으로 이루어져
있으며, 선호되는 답이 나오면 거기서 멈춥니다.

1. **retrieval과 in-context example을 곁들인 단일 LLM 호출을 측정해 보았습니까?** [T1]은
   그것으로 충분한 경우가 많다고 말합니다. 답이 아니오라면 여러분은 무엇을 개선하고 있는지
   아직 모르는 것이고, 만들게 될 agent는 아무것과도 비교되지 않을 것입니다.
2. **대신 prompt를 개선해 보았습니까?** [T1]은 몇 달에 걸친 multi-agent 작업이 더 나은
   prompting과 대등했다고 보고합니다. 가장 값싼 실험이자 가장 자주 건너뛰는
   실험입니다.
3. **단계들이 미리 알려져 있습니까?** [T1] 그렇다면 그것은 정의상 workflow이며, 미리 정해진
   code path가 같은 결과를 주면서 망가질 때 stack trace를 남깁니다.
4. **작업이 진짜로 독립적인 갈래로 나뉩니까?** case 03이 [T1] 이 접근은 병렬적인 갈래로
   나뉘는 문제에 적합하며 coding처럼 얽힌 작업에는 덜 효과적임을 보여 줍니다. 갈래들이 서로
   대화한다면 여러분은 쓸 수 없는 격리에 값을 치르고 있는 것입니다.
5. **그 교환을 감당할 수 있습니까?** [T1] agentic system은 더 나은 작업 성능을 위해 지연과
   비용을 맞바꿉니다. 그것은 양면이 있는 교환이며, case 03이 [T1] 비용 쪽의 측정된 크기를
   하나 제시합니다. chat 상호작용의 대략 15배에 달하는 token입니다.
6. **동작했는지 판별할 방법이 있습니까?** case 04는 oracle이 있을 때의 설계가 어떤 모습인지
   보여 주고, case 03은 oracle이 없을 때 evaluation이 얼마나 드는지 보여 줍니다. agent를
   평가할 수 있게 되기 전에 agent를 만들면, 2번 항목으로 충분했을지 여부를 알 수 없게
   됩니다.

[T1] 이 post는 위의 모든 것을 감안하고도 verification subagent가 여전히 가치 있는 조건들을
명시합니다. orchestrator가 덜 유능할 때, verification이 특수한 tool을 필요로 할 때, 또는
명시적인 verification checkpoint를 원할 때입니다. [T1] 또한 그것들이 작동하는 이유도
제시합니다. verification은 본래 최소한의 context 전달만을 요구하기 때문입니다. [T3] 우리의
해석은 이 마지막 구절이 실제 선택 규칙이며 일반화된다는 것입니다. 인계에 적은 context가
필요한 부분은 위임하고, 많은 context가 필요한 부분은 붙들고 있으라는 것입니다.

## 열두 개의 dimension

아래는 고정된 pipeline을 기술합니다. 다른 case들보다 짧은데, workflow는 대부분의
dimension에 대해 할 말이 적기 때문이고, 그 짧음이 바로 요점입니다.

### 1. Problem and success criteria

[T3] 코드를 작성하는 시점에 단계들이 알려져 있는 작업입니다. 성공은 전체뿐 아니라 단계별로도
정의됩니다. 각 단계가 assert할 수 있는 고정된 입력과 출력 계약을 갖기 때문입니다.

### 2. Autonomy level

[T1] workflow입니다. LLM과 tool이 미리 정해진 code path를 통해 조율됩니다. 스펙트럼의
정의적인 한쪽 끝이며, 라이브러리의 다른 모든 case는 그 반대편 어딘가에 놓입니다.

### 3. Observation space

[T3] 단계별로 고정되어 있으며 코드가 결정합니다. 한 단계는 전달받은 것을 봅니다. 탐색
단계가 없으므로, 예상 못 한 자료를 찾아내는 능력도 없고 그것을 찾느라 예산을 낭비하는
능력도 없습니다.

### 4. Action space

[T3] 코드가 호출하는 것이 코드가 호출하는 순서대로입니다. 모델은 텍스트를 기여할 뿐 행동을
선택하지 않습니다. case 01의 안전 관련 질문 대부분이 사라지는 지점이 이 dimension입니다.
행동을 고를 수 없는 모델은 해로운 행동도 고를 수 없기 때문입니다.

### 5. Tools and agent-computer interface

[T3] tool을 모델이 고르지 않고 프로그램이 호출하므로 tool 선택 문제가 존재하지 않습니다.
description이 언제 호출해야 하는지 말하지 않아 subagent가 한 번도 호출되지 않는 case 01의
실패 부류 전체가 여기에는 없습니다. interface 설계 작업은 모델에게 tool을 설명하는 일에서
컴파일러와 test suite를 위해 단계 계약을 정의하는 일로 옮겨 갑니다.

### 6. Context strategy

[T3] 코드가 단계별로 구성하며 구조적으로 한계가 정해져 있습니다. pipeline이 축적하도록
작성되지 않는 한 아무것도 축적되지 않으므로, case 01과 03이 설계 예산의 대부분을 쓰는 context
전략이 무엇을 다음 단계로 넘길지에 대한 결정으로 대체됩니다.

### 7. Memory and state

[T3] 명시적입니다. 상태는 pipeline이 단계 사이로 나르는 것이며, 평범한 프로그램 변수나
저장소에 담기고, 소스에서 보이며, 테스트할 수 있습니다.

### 8. Control flow

[T1] 미리 정해진 code path입니다. 이 archetype의 정의이며 이 목록의 다른 모든 속성의
원천입니다.

[T3] 우리의 해석은 이것이 가장 먼저 결정할 가치가 있는 dimension이라는 것입니다. workflow의
실패에는 줄 번호가 있고 agent의 실패에는 transcript가 있습니다.

### 9. Error handling and recovery

[T3] 평범한 소프트웨어 error handling입니다. 예외, retry, timeout, 그리고 언어와 framework가
이미 제공하는 것들입니다. 실패한 단계는 당직 엔지니어가 전에 본 적 있는 방식으로
실패합니다.

### 10. Human involvement and permissions

[T3] 코드가 사람을 놓는 자리에, 결정적으로 놓입니다. workflow의 승인 단계는 매번, 같은
자리에서 실행되며, 이는 case 01의 어떤 permission 장치보다도 강한 보장입니다. 모델이 그것을
우회할 수 있는 mode가 아예 없기 때문입니다.

### 11. Evaluation

[T3] 단계별로 그리고 전체로 평가합니다. 고정된 pipeline은 평범한 소프트웨어를 테스트하듯
fixture를 써서 단계별로 테스트할 수 있습니다. 모델이 control flow를 주도하는 이 라이브러리의
어떤 case도 그렇게 할 수 없으며, 이는 상당하면서도 습관적으로 과소평가되는 이점입니다.

### 12. Cost and latency budget

[T1] agentic system은 더 나은 작업 성능을 위해 지연과 비용을 맞바꿉니다. [T3] 그 역에 대한
우리의 해석은 이렇습니다. workflow는 지연과 비용을 지키는 대신, 작성자가 예상하지 못한
입력에서의 작업 성능을 포기합니다. 그것이 교환의 전부이며 한 줄로 진술됩니다. 자신이 그
교환의 어느 쪽을 왜 고르고 있는지 말할 수 있어야 합니다.

## Failure modes

전부 [T3]이며 archetype으로부터 추론한 것입니다.

- **code path가 다루지 않는 경우.** workflow는 작성자가 상상한 입력을 처리합니다. 예상하지
  못한 입력은 적응적인 시도를 낳지 않고, 애초에 그것을 위한 것이 아니었던 경로를 통해 틀린
  답을 낳습니다.
- **입력 분포가 표류할 때의 조용한 성능 저하.** pipeline은 계속 돌고 계속 결과를 반환하며,
  더 이상 데이터에 맞지 않게 된 단계는 스스로를 드러내지 않습니다. 같은 표류에서 실패하는
  agent는 대개 더 시끄럽고 그래서 더 일찍 눈에 띕니다.
- **경직화.** 새로운 경우마다 분기가 하나씩 늘어납니다. 분기가 충분히 쌓이면 미리 정해진
  code path는 아무도 이해하지 못하는 결정 트리가 되고, 실패에 줄 번호가 있다는 원래의 이점은
  이미 소진된 상태입니다.
- **틀린 이유로 옳기.** 더 단순하다는 이유로 선택되고 잘 돌아간다는 이유로 유지된 workflow는
  그것을 옳게 만들었던 제약보다 오래 살아남을 수 있으며, 이를 잡아내는 검토는 위의 체크리스트를
  다시 돌리는 것입니다.

## 훔쳐 올 것 하나

무엇을 설계하기 전에 단일 호출 baseline을 측정하십시오.

[T1] retrieval과 in-context example을 곁들인 단일 LLM 호출을 최적화하는 것으로 충분한 경우가
많고, [T1] 여러 팀이 몇 달이 지나서야 단일 agent에 대한 개선된 prompting이 정교한 multi-agent
architecture와 동등한 결과를 냈음을 발견했습니다. [T3] 우리의 해석은 두 문장 모두에서 핵심이
되는 단어가 비교적이라는 점입니다. 이들은 baseline에 대한 주장이며, baseline을 한 번도 만들지
않은 팀은 그 비교를 할 수 없고 따라서 자신이 둘 중 어느 상황에 있는지 알 수 없습니다.
baseline은 전체 과정에서 가장 값싼 산출물이기도 하며, 그래서 건너뛰기를 옹호하기가
어렵습니다.

## 따라 하지 말 것 하나

진짜로 열린 작업에 적용된 고정 pipeline입니다.

[T3] 우리의 해석은 이 case가 그것이 반대하는 case들만큼이나 과도하게 적용되기 쉽다는
것입니다. 미리 정해진 code path는 단계를 알 수 있을 때 옳으며, 경우를 열거하는 일이 더 이상
가능하지 않게 되는 바로 그 지점에서 부담이 됩니다. 이는 위의 경직화 실패를 이르게 본
것입니다. 체크리스트는 양방향으로 돌아갑니다. 질문은 agent가 일반적으로 과용되는가가 아니라 이
작업의 단계를 알 수 있는가이며, 확신에 찬 아니오도 확신에 찬 예만큼이나 하나의 답입니다.
