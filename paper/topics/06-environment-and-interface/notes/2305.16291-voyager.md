# Voyager: An Open-Ended Embodied Agent with Large Language Models

<https://arxiv.org/abs/2305.16291>

Wang, Xie, Jiang, Mandlekar, Xiao, Zhu, Fan, Anandkumar. NVIDIA, Caltech,
UT Austin, Stanford, UW Madison. 2023.

## Core ideas

A lifelong-learning agent in an open world with no fixed goal, built from
three modules and no gradient updates. The model is queried as a black
box throughout; nothing is finetuned.

- **Automatic curriculum.** The agent proposes its own next task based on
  its current skills and what the world around it looks like, so it
  learns to gather what is nearby before reaching for what is not. This
  is the module that makes open-endedness tractable: without a goal, the
  agent has to manufacture one.
- **Skill library.** Mastered behaviours are stored as **executable
  code** and retrieved for reuse. Because skills are programs, they are
  compositional — a new skill can call existing ones — and the library
  grows rather than overwrites, which is why the paper claims it avoids
  catastrophic forgetting.
- **Iterative prompting.** A skill is written, run, and revised using
  three distinct signals: **environment feedback**, **execution errors**,
  and **self-verification** of whether the task was actually achieved.

**The action space is code.** That is the choice everything follows from.
A primitive action is a single step and cannot be reused; a program is a
named, parameterized, composable unit. Making actions programs is what
turns experience into a growing vocabulary instead of a growing
transcript.

The strongest result is transfer: the library learned in one world lets
the agent solve novel tasks in a **fresh world** it has never seen, which
methods without an accumulating store struggle to do. What accumulated
was capability, not recollection.

## What problem it solves

Agents built on frozen models were not lifelong learners. They could plan
and act, but they did not acquire, refine, and carry forward what they
had learned across long spans. Reinforcement learning does accumulate,
but on primitive actions, and pays for it in systematic exploration,
interpretability, and generalization.

Voyager's answer is that if skills are code and the store is a library,
accumulation is a retrieval problem rather than a training problem, and
the results stay readable.

## Limitations

The paper's own list is unusually concrete.

- **Cost.** The strong model is expensive, and the method needs it: the
  weaker model's code generation is not good enough, so this is not
  something you can run cheaply.
- **Getting stuck.** The iterative prompting loop sometimes fails to
  produce a working skill. The curriculum's answer is to come back to the
  task later, which is a real mitigation and not a fix.
- **Self-verification fails too.** It sometimes misses a valid success
  signal, so the module that decides whether a skill worked is itself
  unreliable.
- **Hallucination in two places.** The curriculum proposes tasks that are
  impossible because the items do not exist, and the code generator
  invents API functions that were never provided and uses materials in
  ways the world does not permit.

Those last two are the general shape of the problem: an agent that writes
its own goals can write unreachable ones, and an agent that writes its own
actions can write invalid ones.

## What this means in practice

1. **Make reusable work a program, not a memory.** This is the idea to
   carry. A transcript of what an agent did is not reusable; a named
   function is. If your agent solves the same shape of problem
   repeatedly, the artifact worth storing is the procedure, and it should
   be callable rather than re-derivable.

2. **Three feedback signals, and keep them separate.** Execution errors
   say the code is wrong. Environment feedback says the world did not
   change as expected. Self-verification says the goal was not met. They
   fail independently and they call for different repairs, so collapsing
   them into one retry loses the information that tells you which repair
   to try.

3. **Self-verification is the weakest link and needs a check outside the
   model wherever one exists.** The paper reports it missing a success it
   should have caught. Where a deterministic check exists — a test, a
   query, a state assertion — prefer it, and reserve model judgment for
   what cannot be asserted.

4. **A self-generated curriculum needs a feasibility filter.** The agent
   proposed goals for items that do not exist. Anything that lets a model
   set its own objectives needs a validity check against what the
   environment actually offers, or it will spend its budget on the
   impossible and report the failure as difficulty.

5. **Validate generated actions against the real API surface.** The
   generator called functions it had not been given. That is cheap to
   catch mechanically before execution, and it is the same discipline as
   validating a generated plan before running workers.

6. **A skill library needs curation, which the paper does not address.**
   Growing forever is presented as a virtue, and in a benchmark it is.
   In a system, a library of self-written functions accumulates near
   duplicates and subtly wrong entries, and a wrong skill that gets
   retrieved is worse than no skill. Storing is the easy half.

7. **The transfer result is the one to take seriously.** Carrying the
   library into an unseen world is what distinguishes accumulation from
   overfitting to one environment. If you build something like this, test
   it somewhere it was not built.

## What it leads to next

Nothing in this library extends it directly. Backwards, it takes the loop
from **2210.03629** and gives the environment something that persists
between runs.

Read alongside **2405.15793**, the other paper in this topic and the
mirror image: Voyager holds the environment fixed and grows the agent's
vocabulary, while SWE-agent holds the agent fixed and redesigns the
interface it acts through. Both conclude that the action surface is a
design variable; they change different halves of it.

Read against **2304.03442** for what accumulates: recollections that make
behaviour believable, versus skills that make behaviour capable.

## Connection to the lab

`papers.yaml` maps this to
`labs/track-3-autonomy/12-agent-loop`, and the mapping is about what
happens when the loop is allowed to run without a fixed goal.

**The lab's subject is limits, and this paper is the case that needs
them most.** An agent with a self-generated curriculum has no natural
termination: finishing a task produces the next task. The lab's
insistence on several independent budgets — steps, cost, wall-clock —
with whichever binds first stopping the run and the run reporting which
one it was, is the only thing standing between open-ended exploration and
an open-ended bill. The lab's phrase for a loop without a ceiling applies
directly here.

**`detect_no_progress` is the mechanical version of the paper's getting
stuck.** The paper reports the loop failing to produce a working skill
and relies on the curriculum revisiting the task later. That is a policy,
and it needs a detector to trigger it: hashing recent action and
observation pairs and noticing the window has stopped changing is how you
know to put a task down rather than grinding on it.

**`run_tool_with_retry`'s split maps onto point two.** Retrying is the
harness deciding to try again, and returning the error to the model is
the model deciding what to do next. This paper's three signals sit on
that boundary: an execution error is often worth a mechanical retry,
while a self-verification failure is information the model has to act on.
