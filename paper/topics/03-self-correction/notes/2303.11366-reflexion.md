# Reflexion: Language Agents with Verbal Reinforcement Learning

<https://arxiv.org/abs/2303.11366>

Shinn, Cassano, Berman, Gopinath, Narasimhan, Yao. Northeastern
University, MIT, Princeton University. 2023.

## Core ideas

Reinforce the agent **without touching the weights**. A conventional
reinforcement learning loop turns a reward into a gradient; this turns a
reward into a paragraph. The agent fails, an evaluator produces a signal,
a self-reflection step converts that signal into a written account of
what went wrong and what to do differently, and the account is carried
into the next attempt as context. The paper's phrase for it is a
**semantic gradient signal**: not a direction in parameter space, but a
direction stated in words.

The framework is three models with distinct jobs, and separating them is
the design.

- **Actor.** Generates the text and actions. Can be a chain of thought or
  a ReAct loop; the framework is agnostic.
- **Evaluator.** Scores a completed trajectory. Deliberately plural in
  the paper: exact match for reasoning, hand-written heuristics for
  decision making, a separate model instance as a judge, and
  **self-written unit tests** for code.
- **Self-Reflection.** Takes the trajectory *and* its score and writes
  the lesson. This is the new component, and its job is the hard one.

**Memory is what distinguishes this from a refinement loop.** Short-term
memory is the current trajectory. Long-term memory is the accumulated
reflections, which persist across attempts. The loop runs whole episodes
rather than revising one draft: fail, reflect, try the task again from
the start with the lesson in context.

The paper is direct about why the reflection step is hard: it requires
solving **credit assignment**, identifying which action caused the
failure, and then writing a summary that contains something actionable.
A scalar reward makes credit assignment difficult, and the argument for
language here is that a sentence can say *which* action was wrong and
what should have replaced it, which a number cannot.

The AlfWorld trigger deserves to be copied verbatim into practice. The
agent self-reflects when it has executed the same action and received the
same response for more than a few cycles, or when the action count for
one environment exceeds a ceiling. That is the repetitive-loop failure
named in 2210.03629, detected mechanically, and used as the signal to
stop and think rather than as a reason to abort.

The claimed advantages are specific and mostly hold up: no finetuning;
feedback more nuanced than a scalar; an episodic memory that is
**explicit and interpretable**, unlike a policy; and concrete hints for
the next episode. The paper states its disadvantages in the same
paragraph, which is rare: it depends on the model's self-evaluation
ability or on your heuristics, and it offers **no formal guarantee of
success**.

## What problem it solves

Agents built on a frozen model could not learn from their mistakes. The
available options were in-context examples, which are static, or actual
reinforcement learning, which needs a great deal of compute, time, and
samples, and produces a policy nobody can read.

Reflexion occupies the gap: a learning signal that costs one extra call
per episode, works from a handful of trials, and leaves an audit trail in
plain language.

## Limitations

- **It is policy optimization, so it can settle into a local minimum.**
  The paper says this first. A wrong lesson learned early is carried
  forward and reinforced.
- **Memory is a bounded sliding window**, holding only a small number of
  experiences because of the context limit. Long-run learning is not what
  this is.
- **It rests on self-evaluation, with no guarantee.** Where the evaluator
  is a model rather than a test or a heuristic, the loop inherits every
  weakness of a model judging its own work.
- **Test-driven evaluation has real limits** that the paper enumerates
  for code: non-deterministic functions, impure functions that call
  external services, behaviour that varies with hardware, and anything
  concurrent. Where you cannot write the test, the strongest evaluator is
  unavailable.
- The reproducibility note is a safety warning worth repeating:
  **generated code is executed without being validated first**, so this
  belongs in an isolated environment.

## What this means in practice

1. **The question that picks the pattern: do you have a signal from
   outside the model's own opinion?** Tests, a compiler, a schema
   validator, an environment reward, an exact-match check. With one, this
   shape works and the loop converges on something real. Without one you
   are in 2303.17651, relying on self-critique, which polishes but
   cannot verify. Choose by what signal exists, not by which paper is
   more sophisticated.

2. **The second question: does a failed attempt cost anything?** If
   retrying is free and stateless, refine the draft in place. If the
   attempt consumed an episode against a real environment — calls made,
   state changed, time spent — you need the lesson to survive the
   attempt, and that is what long-term memory is for. Memory across
   attempts is the expensive feature, so make sure you need it.

3. **Separate the three roles even when the same model plays all of
   them.** Actor, evaluator, and reflector have different prompts,
   different inputs, and different failure modes, and a merged prompt
   hides which one broke. This is the practical value of the paper's
   modular formulation, independent of anything about reinforcement
   learning.

4. **Prefer a mechanical evaluator wherever one exists.** The paper's
   evaluator list is ordered by trustworthiness without saying so: a
   passing test is a fact, a heuristic is a rule you wrote, and a model
   judging its own trajectory is another generation. Push as far up that
   list as your task allows before reaching for the model.

5. **Steal the stuck-detection trigger.** Same action plus same
   observation repeating, or a step count past a ceiling, is cheap to
   compute and is the concrete condition that turns a wasted run into a
   learning signal. Note the difference from a plain budget: a budget
   ends the run, this one *starts the reflection*.

6. **Write the reflection down where you can read it.** The interpretable
   memory is not a side benefit, it is the reason to prefer this over an
   opaque policy. The paper's broader-impact section makes the strong
   version of the point: reflections can be monitored to check an agent's
   intent before it uses a tool. A reflection log is an operational
   artifact, not a debug print.

7. **Bound the memory and decide what to evict.** The window is small and
   the paper leaves better structures to future work. Which lessons to
   keep is a real design decision, and the local-minimum failure lives
   exactly here: a confidently wrong reflection that never ages out will
   steer every subsequent attempt.

8. **Run it in a sandbox.** The paper says so about generated code, and
   the general form is that an agent which retries after failing will
   execute more, not less, of whatever it produced.

## What it leads to next

Within this library nothing extends it directly. Reading outward:

- **Lab-side and paper-side, this closes the loop opened by
  2210.03629.** ReAct named the repetitive-loop failure and had no
  mechanism to escape it. This supplies one, and uses ReAct as its actor.
- **2303.17651** is the contemporary with less machinery: same instinct,
  no external signal, no memory, one draft instead of one episode.
- **`07-evaluation`** is where the evaluator question gets taken
  seriously on its own terms, which is the component this paper leans on
  hardest and defends least.

## Connection to the lab

`papers.yaml` maps this to two labs, which again splits the paper.

**`labs/track-1-patterns/06-evaluator-optimizer` is the inner loop.** The
lab's generate, evaluate, thread-feedback-back structure is this paper's
Actor, Evaluator, and Self-Reflection with the memory removed. Its
insistence that criteria be specific and independently gradeable is the
same requirement this paper places on the evaluator, and its warning that
a loop whose second call does not see the critique is merely resampling
is the same point as the reflection being carried in context.

Where the lab stops short is the trial boundary. `refine` improves one
draft; this paper reruns the task. If you extend that lab in one
direction, extending it to carry lessons across whole attempts is the
extension this paper describes.

**`labs/track-3-autonomy/12-agent-loop` is where the trigger lives.**
That lab's `detect_no_progress` hashes recent action and observation
pairs and stops when the window is all repeats. This paper uses the
identical condition for a different purpose: not to stop the run, but to
fire a reflection. Those are two different responses to one detector, and
knowing you have the choice is the useful part. The lab's insistence that
a run report which stop condition fired is what makes the difference
visible.

The lab's separation of retrying a tool from returning the error to the
model is the same distinction one level down: retry is the harness
deciding, reflection is the model deciding, and both need the failure
described well enough to act on.
