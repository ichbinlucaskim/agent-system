# Lab 15 - Evaluation

## 목표

이 lab을 마치면 LLM 시스템을 위한 regression suite를 만들 수 있습니다. 적용 가능한 곳에는 결정적 assertion을, 그렇지 않은 곳에는 rubric 기반 LLM-as-judge 채점을, 그리고 단일 실행의 판정이 아니라 반복 실행에 걸친 pass rate 리포트를 만들 수 있습니다.

## 사전 준비

Lab 00부터 06까지. 개념: lab 06의 evaluator, 그리고 모델 출력이 실행마다 달라진다는 사실.

## 예상 소요 시간

60분에서 90분

## 배경

evaluation suite가 없으면 prompt 변경은 추측입니다. 출력이 달라 보이고, 누군가 더 나아 보인다고 판단하지만, 그 변경이 계기가 된 사례를 고쳤는지 아니면 아무도 확인하지 않은 네 개의 사례를 망가뜨렸는지 아무도 말할 수 없습니다. eval은 그것을 변경 전후로 비교할 수 있는 숫자로 바꿉니다.

결정적 assertion을 먼저, 그리고 가능한 한 많이 작성하세요. JSON이 파싱되는가, 필수 필드가 있는가, 인용 id가 실제로 존재하는 것인가, 답변이 길이 제한 안에 있는가, 거절해야 하는 사례가 실제로 거절하는가. 이런 검사는 비용이 없고 모호하지 않으며 대부분의 회귀를 잡아냅니다.

judge는 assertion으로 확인할 수 없는 것에만 쓰세요. 어조, 출처에 대한 충실성, 설명이 실제로 도움이 되는지 같은 것들입니다. judge 자체도 모델 호출이며 여러분이 측정하려는 그 변동성을 그대로 갖고 있으므로, 구체적이고 독립적으로 채점 가능한 기준의 rubric을 주고 산문으로 된 판정 대신 구조화된 출력을 요구하세요.

단일 실행 결과는 잡음입니다. 같은 입력이 한 번은 통과하고 다음에는 실패할 수 있으므로, 각 사례를 여러 번 실행하고 pass rate를 보고하세요. 다섯 번 중 세 번 통과한 사례는 통과도 실패도 아닙니다. flaky한 사례이며, 어떤 사례가 flaky한지 아는 것이 종합 점수보다 유용할 때가 많습니다.

실패를 보관하세요. 80퍼센트라고만 말하는 리포트로는 아무것도 할 수 없지만, 실패한 네 개의 사례를 지목하고 그것들이 무엇을 반환했는지 보여 주는 리포트로는 할 수 있습니다. 출력을 저장해 두면 suite 전체를 다시 돌리지 않고도 회귀를 진단할 수 있습니다.

실제 실패에서 suite를 키우세요. 누군가 보고한 모든 버그가 하나의 사례가 되면, suite는 인위적인 벤치마크이기를 그만두고 여러분의 시스템에서 실제로 무엇이 잘못됐는지에 대한 기록이 되기 시작합니다.

## 단계

1. `Case`를 정의하세요. id, 입력, 그리고 만족해야 할 결정적 검사 목록으로 구성해서 사례가 손으로 쓴 테스트 함수가 아니라 데이터가 되게 합니다.
2. `run_deterministic`을 구현하세요. 각 검사를 출력에 적용하고 검사별 결과를 실패 사유와 함께 반환합니다.
3. `judge`를 구현하세요. 구조화된 출력으로 rubric에 따라 출력을 채점하고 점수와 그 근거를 반환합니다.
4. `run_suite`를 구현하세요. 모든 사례를 `runs`번 실행하고 결정적 결과와 judge 결과를 모으며 원본 출력을 보관합니다.
5. `format_report`를 구현하세요. 사례별 pass rate를 출력하고, 0과 1 사이의 사례를 flaky로 표시하며, 실패를 그 출력과 함께 나열합니다.
6. prompt 하나를 바꾸고 suite를 다시 실행한 뒤 두 리포트를 비교하세요. 그 비교가 이 lab 전체의 요점입니다.

## 검증

```bash
pytest labs/track-4-production/15-evaluation/tests -v
```

suite 기계 장치는 stub 출력으로 오프라인 테스트됩니다. 통과했다면 결정적 검사가 실패 시 사유를 보고하고, pass rate가 마지막 실행이 아니라 여러 실행에 걸쳐 계산되며, 간헐적으로 통과하는 사례가 flaky로 표시되고, 리포트가 실패한 모든 사례를 지목하며, 파싱되지 않는 judge 응답이 0점이 아니라 에러로 기록된다는 뜻입니다.
