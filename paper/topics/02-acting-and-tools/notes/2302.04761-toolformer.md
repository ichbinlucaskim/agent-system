# Toolformer: Language Models Can Teach Themselves to Use Tools

<https://arxiv.org/abs/2302.04761>

Schick, Dwivedi-Yu, Dessì, Raileanu, Lomeli, Zettlemoyer, Cancedda,
Scialom. Meta AI Research and Universitat Pompeu Fabra. 2023.

## Core ideas

Where 2210.03629 puts tool use in the prompt, this paper puts it in the
weights. The stated target is a model that decides **which API to call,
when to call it, what arguments to pass, and how to fold the result into
what it writes next** — all learned, from nothing but a handful of
demonstrations per API.

The pipeline has three steps and the third is the idea.

1. **Sample.** For each API, a short prompt asks the model to annotate
   ordinary text with calls it thinks would help. Positions where the
   model assigns high probability to starting a call are kept, and
   several candidate calls are sampled at each.
2. **Execute.** Every candidate call is actually run to get a result. The
   only requirement on a tool is that its input and output are text.
3. **Filter, and this is the whole contribution.** Keep a call only if
   having the call *and its result* in the context **reduces the loss on
   the tokens that follow**, compared with the better of two baselines:
   no call at all, and the call without its result. Everything that does
   not pay for itself is discarded.

Then the surviving calls are interleaved back into the original text and
the model is finetuned on that. Because the augmented corpus is the same
text plus insertions, finetuning does not cost the model its generality.
At inference the model decodes normally until it emits the token that
means a result is expected, generation is interrupted, the API is called,
the response is inserted, and decoding continues.

**The filter is a definition of usefulness, and it is not a human's.**
The paper states this as a design requirement rather than a convenience:
what humans find useful may differ from what a model finds useful, so
usefulness is defined as measurable help in predicting the continuation.
That is a self-supervised signal, which is what removes the annotation
cost that made earlier tool-use work expensive.

The tools chosen are deliberately mundane — question answering,
Wikipedia search, a calculator, a calendar, translation — and they map
onto known and specific weaknesses: stale knowledge, hallucinated facts,
arithmetic, low-resource languages, and no sense of the current date.

## What problem it solves

Before this, teaching a model to use tools cost one of two things. Either
large amounts of human annotation, which is expensive and which encodes a
human's guess about when a tool helps. Or task-specific scaffolding,
which works but does not transfer, so tool use stays bolted onto one
application rather than becoming a general capability of the model.

This paper removes both costs at once. The supervision comes from the
model's own perplexity, and because the training data is general text
rather than task data, the resulting ability is not tied to any task.

## Limitations

The limitation list is unusually load-bearing here, because it is
essentially a list of the things a harness gives you for free.

- **No chaining.** Calls are generated independently, so nothing in the
  finetuning data shows one tool's output used as another's input, and
  the model cannot do it.
- **No interactive use.** It cannot browse a result set, refine a query,
  or take a second look. A single call is issued and its answer is taken.
- **Sensitive to exact wording** when deciding whether to call at all,
  which is the same brittleness prompting has, arriving by a different
  road.
- **Very sample-inefficient.** Processing an enormous quantity of text
  yields only a small number of useful calls for some tools. Whatever
  the yield is, you pay for the whole corpus to find it.
- **Cost-blind.** The decision to call never accounts for what the call
  costs. Every tool is free at decision time, which no tool is.

## What this means in practice

1. **This is the learned answer to tool use, and its limitation list is
   the argument for the other one.** No chaining, no browsing, no query
   refinement: those are the things an agent loop supplies without being
   asked, because a loop can simply run again with the last result in
   context. Read this together with 2210.03629 and the choice becomes the
   actual content of this topic.

2. **The criterion for choosing.** If tools change often or their number
   is fluid, use the harness: adding a tool is a schema and a
   description, and nothing is retrained. If the tool set is fixed and
   the genuinely hard part is judging **when** to call, learning becomes
   worth considering, because that judgment is what this method
   internalizes. In practice the first case is almost everything. The
   second is a minority: a large body of domain-specific tools where call
   timing, not tool availability, is the bottleneck.

3. **The idea that outlives the method is measuring tool usefulness
   instead of arguing about it.** The loss-reduction filter is an
   evaluation design before it is a training trick, and the transferable
   version needs no finetuning at all: fix a set of questions, vary only
   the tool surface, and count how often the right tool gets called. That
   turns tool wording from taste into a number, and it is the one
   experiment worth running on any tool you ship.

4. **A harness has to say out loud what this model learned.** Toolformer
   absorbed when-to-call from data; a prompted agent has no such data, so
   the trigger condition has to be written into the description. This is
   the reason a description stating when to call it beats one stating
   what it does. The learned system had a signal for that decision, and
   the prompted one has only your sentence.

5. **Budget for the yield if you ever do go the learned route.** Sample
   inefficiency is the practical blocker, not the algorithm. A plan that
   assumes useful examples are dense in ordinary text will be wrong for
   most tools, especially narrow ones.

6. **Cost-awareness is yours to add, and it is not optional in
   production.** Tool calls differ enormously in latency and price. A
   policy layer that knows a call is slow or expensive can decline it; a
   model trained only on whether the call helped prediction cannot. This
   is a real advantage of keeping the decision outside the weights.

7. **The text-in, text-out constraint is still with us.** The only
   requirement placed on a tool here is that its inputs and outputs
   serialize to text, and that is still the interface every tool protocol
   in use today is built on. The constraint has aged better than the
   method.

8. **The learned half has largely moved upstream.** Current models arrive
   already trained to use tools, so the capability this paper had to
   manufacture now comes with the model. What that leaves for you is
   almost entirely the harness: which tools exist, how they are
   described, what the schema forbids, and what a failure returns. That
   is the honest reason the criterion in point two resolves the way it
   does.

## Connection to the lab

`papers.yaml` maps this paper to
`labs/track-2-tools-context/07-tool-design-aci`, and the mapping is a
handoff rather than an implementation: what this paper learned, that lab
has to write down.

**`compare_descriptions` is the loss-reduction filter without the
finetuning.** The lab holds a question set fixed, varies only the tool
description and schema, and reports the selection rate for each variant.
The mechanism differs and the epistemics are identical: both refuse to
decide whether a tool is well specified by looking at it, and both
replace that judgment with a measurement. The lab says this is what turns
tool wording from a matter of taste into a number, and this paper is the
same instinct applied to training data.

**The trigger-condition rule is the harness paying for what this paper
learned.** The lab's example contrasts a description that states a
capability with one that states when to call it and what the alternative
sources do not contain. Toolformer never needed that sentence, because
the filter found the positions where calling helped. A prompted agent has
no filter, so the sentence is the substitute, and that is why it measures
better.

**`format_tool_error` covers a case this paper cannot reach at all.**
Toolformer issues a call and takes the answer, with no interactive use
and no refinement. The moment an error is returned as text that the model
reads and acts on, you are in the loop from 2210.03629, and the error
message is a prompt. The lab's contrast between an unhelpful failure
string and one that names the problem and lists valid inputs is the whole
difference between a tool that can be recovered from and one that ends
the run.

The lab's rule that the model sees only the name, the description, and
the input schema is the sharpest statement of what the harness route
costs. Those three fields have to carry everything Toolformer would have
absorbed from data.
